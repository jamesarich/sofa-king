# Architecture

Sofa King is a Kotlin Multiplatform project. One Compose Multiplatform UI on Material 3 Expressive runs on Android TV, Google TV and Android phones, on Linux, macOS and Windows desktops, on iOS, and in browsers through Wasm or JS.

## Modules

| Module | What it holds | Targets |
| --- | --- | --- |
| `core` | Models, the server API and the server connection, repository, playback sessions, lineup cache, settings store and the ViewModels (`LineupViewModel`, `LibraryViewModel`, `RecordingsViewModel`). No Compose. | Android, JVM, iOS, macOS, tvOS, watchOS, Linux, js, wasmJs |
| `ui` | Every screen, the app shell, the guide and player logic, the app graph, and the desktop, web and iOS entry points | Android, JVM, iOS, js, wasmJs |
| `androidApp` | The Android application: manifest, launcher and TV banner, `SofaKingApplication` and `MainActivity` | Android |
| `baselineprofile` | The Baseline Profile generator for `androidApp`, which [development](development.md#baseline-profile) runs on a device | Android |
| `iosApp` | The SwiftUI host for the `SofaKingUi` framework, as an XcodeGen spec | iOS |
| `tvosApp` | The SwiftUI Apple TV app on the `SofaKingCore` framework (`SofaKingTv` in `core/tvosMain`), as an XcodeGen spec | tvOS |

`core` targets everything its dependencies publish, so a native host such as a SwiftUI tvOS app can use the same data layer without Compose. Windows native is absent because DataStore has no mingw build; the JVM covers Windows desktops.

All source lives under `dev.jamesrich.sofaking`. Code is in `commonMain` unless it needs a platform API; each `expect` has one `actual` per platform source set (`androidMain`, `jvmMain`, `iosMain`, `webMain`). `fileMain` (Android, JVM and native) holds the stores that live in files, since the web targets keep theirs in the browser.

## Data flow

```text
AppStorage → DataStoreSettingsStore → ServerConnection → SofaKingApi (Ktor), PlaybackSessions, RecordingSchedule
                     ↓                         ↓
               LineupViewModel ← SofaKingRepository     LibraryViewModel, RecordingsViewModel
                ↓          ↓
          LineupCache    GuideScreen / PreviewVideo / PlayerScreen → PlaybackSessions → LivePlayer (/media relay)
```

The cache loads first on startup or server change: its channels publish as soon as the file is read, marked `guideLoading`, and its programmes follow once decoded on the default dispatcher, which takes seconds for a full guide on a TV. The catalog publishes channels before the guide query completes. The catalog is fetched with its ETag, so an unchanged lineup is a header round trip. The guide is queried in chunks of at most 200 channels over 24 hours from the half hour containing the load time, pinning the revision the first chunk returned on the rest, which run four at a time, and restarting without one on `409 RESYNC_REQUIRED`. A channel the guide answers as `removed` left the lineup after the catalog was read: it drops from the lineup and the next load runs after one minute. Mapping applies the [channel rule](usage.md#channels) through `playbackEligible` and `displayNumber`, sorts the channels by number, files each under every non-blank tag (Other when it has none), resolves each logo's server-relative path against the configured server address, and discards programs with invalid timestamps or nonpositive durations. Successful loads update the cache and repeat every three hours. A day the guide jumps to beyond the live window is queried once over the same path (`loadGuideWindow`), merged into the lineup's guide beside the live window, never cached, and dropped once the live window passes it. Failed loads retain the available lineup and retry after one minute. Without a valid server address the lineup state is `Unconfigured`.

Network and cache file work run on the IO dispatcher (the default dispatcher on the web); JSON decoding, the lineup's mapping and the merge of extra guide days run on the default dispatcher, so the main thread only sets state. State flows one way: ViewModels expose immutable `StateFlow`s, each destination collects the ones it shows with `collectAsStateWithLifecycle`, and user actions go back as ViewModel calls: setters return nothing and log a write the settings store refuses, and a short action whose result matters only while its screen is up, such as Record, Delete, a library search or opening a stream, is a `suspend` call the screen awaits. Work that must outlive a screen, such as claiming a pairing code, runs in `viewModelScope` and reports its outcome as state; process-wide work, the server connection's, runs in `AppGraph`'s main-thread scope, started by the first ViewModel, and logs a failure nothing else handles rather than crashing the process. Canceling a load cancels its HTTP call, including while reading the response body.

## Storage

| Platform | Settings | Lineup cache |
| --- | --- | --- |
| Android | `files/datastore/settings.preferences_pb` | `files/lineup-cache.bin` |
| Desktop | `<dir>/datastore/settings.preferences_pb` | `<dir>/lineup-cache.bin` |
| iOS | `datastore/settings.preferences_pb` under Application Support | `lineup-cache.bin` under Application Support |
| Apple TV | `NSUserDefaults`, under `sofaking.preferences`, since tvOS may purge any file; an older build's file under Caches moves there on first read. The recent channels are also written as JSON into the `group.dev.jamesrich.sofaking` app group's defaults for the Top Shelf extension | `lineup-cache.bin` under Caches |
| Web | DataStore's localStorage store for the page's origin, under `sofaking.preferences`; an older build's `sofaking.settings` entry moves there on first read | DataStore's localStorage store under `sofaking.lineupCache` |

On a desktop, `<dir>` is the OS's per-user app data directory:

| OS | Directory |
| --- | --- |
| Linux | `$XDG_DATA_HOME/sofa-king`, or `~/.local/share/sofa-king` when `XDG_DATA_HOME` is unset or blank |
| macOS | `~/Library/Application Support/Sofa King` |
| Windows | `%APPDATA%\Sofa King`, or `Sofa King` in the home directory when `APPDATA` is unset |

Both are DataStores, so writes replace the file whole and a file that does not read is replaced with an empty one. DataStore allows one instance per file, so the graph holds each as a single and each entry point starts the graph once. The lineup cache is one kotlinx-serialization protobuf record, which every platform reads and writes the same way, with the programmes nested as one encoded message (field 4) so reading the file copies them as bytes and decodes them only on demand; a file from an older build, with the programmes in field 3, still reads; a cache that does not decode, such as one an older build wrote with a version header, is replaced and the lineup refetched.

## Launch

A cold start shows the loader until the settings are known, and for Live until the lineup is too, then decides once (`launchTarget`): Open on start's Where I left off reopens the tab remembered on the device (`AppSettings.lastTab`, written whenever the open tab changes), which on Live is the last watched channel full screen through the normal session path when the lineup has it; Library or Recordings open on their first page with nothing playing, and give way to Live if the server turns out not to offer them; a first run, a channel the lineup lost, an unconfigured or unreachable server open the guide. With no server set, the guide shows its Connect message and focuses the header's Settings button (`homeFocusFor`). The guide and its preview do not compose before that decision, so no preview session is opened only to be replaced. Back from that player shows the guide focused on the channel being watched.

## UI

Screens use multiplatform Material 3 Expressive components (`Button`, `Switch`, `FilterChip`, `Surface`, `OutlinedTextField`, `LoadingIndicator`) under `MaterialExpressiveTheme` with the expressive motion scheme. `tvFocus` adds the D-pad focus cue, a scale and an outline ring; guide cells keep their size and change color instead. Strings are Compose resources in US English. Channel logos and program images load with Coil over the API's connection pool (`ui/Images.kt`), decoded to their slot's size and kept in Coil's memory cache and, except on the web, its disk cache. Back goes through NavigationEvent: the remote's Back on Android, the swipe on iOS, Escape on desktops and the web.

The top-level destinations are Live (the guide), Library, Recordings and Settings. On a TV, the tabs are pills in the header beside the app's name, so the guide keeps its full width and Up from its chips reaches them as it reaches the header's buttons; Settings is the header's one button. The header has no Refresh: the lineup reloads every three hours and on resume, Library reads its shelves each time its tab opens, Recordings its list, and Settings › Server › Reload asks at once. Elsewhere Material's expressive `NavigationSuiteScaffold` (`material3-adaptive-navigation-suite`) draws them as a short bar on a compact window and a rail otherwise, and slides it away over the full-screen players only. Library shows when the server's bootstrap reports the `library` capability, and hides once the library home shows the server has no libraries; Recordings shows when it reports `recordings`. Back from Library's or Recordings' pill opens Live with `Arrival.inHeader`, which keeps focus on the Live pill (the guide holds its first focus and the preview until focus comes down), so one more Back exits; leaving Settings does the same with focus on the Settings button. The Guide key on their pages opens the guide at Now. Back from an item, a recording or a search result returns focus to it (`Route.focusKey`); a Library or Recordings page that has nothing to focus a few frames after it opens (still loading, or empty) gives focus to its pill, and with focus on the pill the page scrolls back to its top.

Routing is Navigation 3 (`navigation3-ui`). `Navigation` holds one back stack of `Route`s per tab, each starting at the tab's first page, and is saved as state; `NavDisplay` shows Live's stack with the open tab's on top, so Back from a tab's first page lands on the guide. A page's parent is the entry below it, so Back returns where the viewer came from, Settings included, and a page already on the stack is returned to rather than opened twice. Each tab keeps its pages' saved state, so it opens again where it was left, and picking the open tab again closes its pages. One-shot arrival details (`Arrival`: the item, chip or channel to focus on return, the guide's Now and search) sit beside the stacks and are not restored. Back on the guide and on a tab's first page is still the page's own (`guideBackAction`, `tabBackAction`): it climbs to the header's open tab first. Each page has its entry's own lifecycle, while the players and the preview read the app's (`LocalAppLifecycleOwner`), so they save their place and free the stream only when the app leaves the foreground, not on every Back. A TV cuts between pages; other windows cross-fade. Entering the library or Recordings stops the guide's preview and releases its session, and ON_START resumes a live stream only on the guide and the live player.

## Guide

The grid covers 24 hours from the half-hour at which it opens. It moves the window when the current time leaves that range. Rows share a horizontal scroll position; Up/Down preserve the time cursor. Filter, search, cursor, scroll and focused channel are saved across full-screen playback. Voice search goes through Android's `RecognizerIntent` activity; the manifest declares the query so the app can tell whether one is installed, and the text field is the fallback there and on every other platform.

Models are immutable; the UI module's Compose stability configuration marks the core models stable. A minute clock that ticks on the wall-clock minute updates the guide and current-program displays. Focus requests for lazy items wait until their nodes attach. When guide data arrives after the channels, the focused cell's details are refreshed from the new row and focus returns to the cell at the time cursor.

## Playback

The app holds one `LivePlayer`. Preview and full-screen playback share it, so opening the previewed channel preserves the stream. Preview tuning debounces focus by 350 ms, and the preview shows the channel's card over the last channel's picture until the new stream is set. Tune effects wait for the host to reach STARTED. `PreviewDwell` holds the preview's rest timers on a monotonic clock: muted on tune, sound after 5 s, full screen after 10 s through the same promote handoff as OK; a key press or a focus move restarts both and mutes, focus off the grid or an open search stops them, nothing opens while the host is stopped and ON_START restarts the rest, and the channel the player was just left on is suppressed until another channel takes focus.

| Platform | Player | Plays | Captions | Media session |
| --- | --- | --- | --- | --- |
| Android | Media3 ExoPlayer | MPEG-TS, HLS | CEA-608/708, drawn by the app with per-channel timing | MediaSession |
| Desktop | libVLC through vlcj | MPEG-TS, HLS | Drawn into the picture by libVLC | None |
| iOS | AVPlayer | HLS | Drawn by AVPlayerLayer in the iOS caption style | Now Playing with the channel logo, and remote commands |
| Apple TV | AVPlayer in `AVPlayerViewController` | HLS; library files as MP4 or HLS | The system player's | The system player's; its transport bar carries the favorite toggle and a channel menu (recent, favorites, all) that tunes without leaving the player |
| Web | `<video>`, drawn into the Compose canvas through WebGL | HLS where the browser plays it natively | The browser's in-band text tracks, drawn by the app in the canvas and by the browser in the element-view fallback; Safari exposes CEA-608, Chrome's built-in HLS exposes none | Page title and the Media Session API (metadata, play, pause, next, previous) |

On the web the `<video>` element stays out of the page: each frame the video presents (`requestVideoFrameCallback`, or every display frame where a browser lacks it) is uploaded into a texture of its own size and blitted into a `WebGLRenderTarget`, which draws as a Compose image, so overlays draw over the picture. Browsers refuse autoplay with sound before a user gesture; the player then plays muted and restores the sound on the first key or pointer press. Without WebGL2, or when a cross-origin server sends no CORS headers on media, the player falls back to an HTML element view, which Compose stacks above its canvas and so hides the full-screen overlays.

`LivePlayer` exposes state as flows (`status`, `errors`, `cues`), so screens collect them instead of registering listeners. The desktop, iOS and web players share `StreamLivePlayer`: the held stream, the status and error flows and the live-resume rule, under which a play after more than 30 seconds paused on a live channel reopens the stream at the edge; Android's player keeps its item in Media3 and seeks to the edge instead. The full screen keeps the display awake while it plays (`KeepScreenOn`): the view's flag on Android, the idle timer on iOS, a screen wake lock in the browser and the OS power API on Windows and macOS; a Linux desktop follows its own idle settings. The window around a full-screen player comes from `rememberPlayerWindow`: on Android it hides the system bars and, on a phone or tablet, hands the player to Jetpack's core-pip, which shrinks it into picture-in-picture when the viewer leaves the app; the activity stays started there, so the stream plays on, and closing the window stops it, which the app's ON_STOP handles as it does behind another app. A desktop window and a browser page go full screen through `WindowFullScreen`, which their entry points pass to `App`. The desktop player looks for libVLC and loads it on its own command thread, once per process, so the window never waits on the search, which walks the library directories where VLC is missing. A desktop without libVLC gets a player whose every prepare fails with `VLC_NOT_INSTALLED`, so the screens show their failure cards and the rest of the app works.

Every stream comes from a playback session. `PlaybackSessions` holds at most one: the preview opens it with `preview` intent, and OK on the previewed channel promotes the same session to `watch` with a PATCH, so the player keeps its item and nothing reloads. Tuning another channel releases the held session, then opens the next. The lease is renewed every 15 seconds with an empty PATCH, inside the 45-second preview lease. A renewal that returns a new descriptor epoch, or `410 SESSION_EXPIRED` followed by a reopen, is published on `replaced`; the app swaps the held item's URL and prepares it. On Android and iOS, the player reports a 410 from the media relay as an error whose first reconnect runs without the backoff delay, and the preview tunes again up to twice before it shows Preview unavailable; the desktop and web players report no HTTP status, so a failure on them waits out the backoff in the player and shows Preview unavailable at once in the preview. Tuning again re-reads the session and takes the current URL.

Items carry the channel id and the MIME type from the descriptor, translated to Media3's HLS constant, so Media3 never sniffs an HLS playlist as MPEG-TS. Session opens run to completion even when the tune is canceled, and a canceled tune releases what it opened.

ON_STOP and Settings stop playback and release the session; Settings forgets it, ON_STOP remembers the channel and intent. ON_START opens a fresh session for that channel, points the held item at its URL and prepares it while preserving paused intent; if the reopen fails, the stale item is prepared and the screen's reconnect takes over. In a browser the app's lifecycle follows the tab's visibility (`rememberAppLifecycleOwner`): a hidden tab is stopped whatever focus says, and a tab shown again counts as started only after 500 ms visible, so a page flashed into view opens no session. A closing tab cannot wait for the stop's release, so `ReleaseOnPageExit` sends the held session's DELETE itself on `pagehide`, as a keepalive request (`PlaybackSessions.exitRelease`). A new server address or token releases the session before anything tunes on the new server. The app releases the player on disposal. `PlayerScreen` and `VodPlayerScreen` hold the media session while they are composed and the app is started (`LifecycleStartEffect`), so no session outlives the stopped player. The newest page to open it holds it (`NewestMediaSession`): Up next replaces the page while the two cross-fade, and the older page's close then does nothing. There is no background playback service. Sound follows the volume: Android asks for audio focus, and iOS takes the Playback audio session category, only while the player is audible, so the muted preview never stops other apps' sound.

A `PlaybackStream` marked `seekable` (a recording or a library file, never a live channel) can be moved through: `isSeekable`, `positionMs`, `durationMs` and `seekTo` work on every engine, `durationMs` grows while a recording is still being made, and `play` after a pause resumes where it paused instead of rejoining live. `PlaybackSessions.play` opens a library item with the engine's `playbackProfile` (the containers, codecs, height and HDR it plays as they are; on Android the codecs Media3 finds a decoder for, and HDR only when an HEVC decoder takes HDR10's profile and the display shows HDR10) and releases whatever was held, live or not; tuning a channel releases an item the same way. The server answers with the file itself or with HLS it copies or converts from the asked start. A converted stream's 0 is that start (`offsetMs`), so the item's position is the player's plus `offsetMs`; a file played as it is starts at 0 and the player seeks to `startAtMs` once it is loaded. A seek past what the server has written calls `restartAt`, which restarts the conversion there under a new URL. The item's lease is renewed every 15 seconds; a dropped one, and a reopen after ON_STOP, open the item again where the player last reported it was (`reportPosition`). `LibraryViewModel` saves that position on the server every 10 seconds while an item plays and at once when it stops; the server marks it watched past 90% and clears it under 5%. `VodPlayerScreen` plays the held item for library files and recordings. Left and Rewind step back 10 seconds and Right and Fast Forward 30, a held key a minute and then five; the presses build a target on the seek bar that applies once they rest for 0.7 seconds or on OK. The seek plan (`vodSeekPlan` in `VodPlayback.kt`) seeks in the player when the target is in the stream it holds and calls `restartAt` otherwise. Breaks passed in `VodTitle.markers` show on the bar, and with `autoSkipBreaks` playback that runs into one jumps to its end; a seek into a break stays there. While another app is in front the screen saves the position, and back in front it reopens the item there itself, so the app's ON_START resume and its replaced-stream handler leave library items to it. Leaving or reaching the end saves the position and releases the session for good. `PlaybackSessions.playRecording` opens a recording the same way, with its id as the stream's `itemId`, and `RecordingsViewModel` saves its position and marks it watched past 90%; the Recordings tab passes the recording's commercial breaks as markers and the Skip commercials setting as `autoSkipBreaks`.

`LivePlayer` also lists the stream's audio tracks and reports what it knows about the stream (`StreamInfo`), which the stream card shows with the session's source and id from the server's descriptor. Channel changes update the info bar at once and tune once presses have rested for 400 ms; the tune stops the player, resolves the session, sets the item and prepares it. Falling behind the live window re-prepares at the live edge inside the player. Other errors and ended streams reconnect with backoff while the player is visible and the host is started. A session refused with `CHANNEL_NOT_FOUND` is not retried: the player asks the ViewModel to reload the lineup, waits for its catalog, and follows the channel to the row with the same number, then the same name; when neither exists it returns to the guide, which shows a short notice. A reload that fails or times out is retried with the reconnect backoff; the dead id is never asked for again except by OK.

On Android the TS extractor declares CEA-608/708 tracks for MPEG-TS sources; HLS sources go through Media3's HLS extractor, which exposes CEA-608 by default. `CaptionSync` and its load control apply per-channel timing (an earlier timing waits for that much buffer, a later one applies at once), and the player picks the preferred text track on every track change. Media3 cues become `CaptionCue`s, whose positioning constants equal Media3's, and the common `Captions` composable draws them in the selected style on the full screen and over the preview. Renderer-thread settings use volatile fields. Video uses Media3 `ContentFrame` and a SurfaceView.

## Server interface

The app uses the [Sofa King server](../../backend/README.md) API through the request and response types in [`contract/`](../../contract/README.md), which the server compiles against too: `GET /api/v1/bootstrap` for the server's capabilities, `GET /api/v1/channels` with `If-None-Match`, `POST /api/v1/guide/query`, `POST`, `GET`, `PATCH` and `DELETE` on `/api/v1/playback-sessions`, `POST /api/v1/pair` to claim a pairing code, `GET` and `PUT` on `/api/v1/preferences/{clientId}`, through which `ViewerSync` keeps the hidden channels, favorites and recent channels in step with the server's copy, the library reads under `/api/v1/libraries` and `/api/v1/library`, `POST`, `PATCH` and `DELETE` on `/api/v1/vod-sessions`, which play recordings too, and `GET`, `POST`, `PATCH` and `DELETE` on `/api/v1/recordings` and `/api/v1/recording-rules`. API requests carry `Authorization: Bearer TOKEN` when a token is set, which a pairing claim has not; media requests under `/media/sessions` and `/media/vod`, and artwork under `/artwork`, carry none. Descriptor URLs are relative and resolved against the server address. The token is stored with the other settings and is never logged or printed.
